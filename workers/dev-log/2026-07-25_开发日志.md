## 💡 一、 本日完成的功能与改进 (Features Delivered)

1. **Twitter/twimg 视频 ID 规范化全路径提取 (Canonical Video ID)**
   - 解决问题：过去仅截取 Tweet 纯数字 ID，丢失了 `amplify_video/xxx/vid/avc1/720x1280/hash.mp4` 目录结构，导致推荐流/数据库导出后无法还原原始 CDN 播放链接。
   - 方案实施：引入 `getCanonicalVideoId` 与 `resolveUrlFromCanonicalId` 辅助工具函数，重构 `JavtwiAdapter`, `PektinoAdapter`, `NextApiAdapter` 以及 `PoolManager.loadDetails()`，无损保留相对 Path 作为规范 ID。
   - Worker 适配：修改 Worker `sanitizeStr` 正则，放行 `/` `@` `:` `=` `?` 等字符，并将校验上限扩展至 256 字符。

2. **Worker 端的 JSON 深度合并 (Deep Merge)**
   - 解决问题：之前的 Worker 执行 SQL `ON CONFLICT(session_id) DO UPDATE SET video_heat = excluded.video_heat` 时，第二次发来的 payload 会直接**覆盖抹掉**上一个视频的热度 JSON。
   - 方案实施：Worker 接收数据时先查询数据库已有的 `action_counts` 与 `video_heat`，通过 JS 在内存中**深度递归合并与秒数/分桶累加**后再写入 D1。经线上实测验证，多次切歌发包后，D1 的 `video_heat` 能无损完整保留所有看过的视频。

3. **前端 Storage 本地持久化缓存 + 1 小时定期上报策略**
   - 解决问题：用户切歌或产生交互时上报频率过高，造成 D1 写入次数配额消耗快。
   - 方案实施：
     - **本地 Storage 缓存**：交互事件与 `videoHeat` 实时在前端 `runtime.storage` / `GM_setValue` / `localStorage` 中同步持久化，**播放切歌与日常交互产生 0 次网络请求，0 次 D1 写入**。
     - **1 小时定期上报**：设定 `ONE_HOUR_MS = 60 * 60 * 1000`。仅当距离上次成功写库满 1 小时且有本地缓存时才向 Worker 刷写；离屏隐藏时设置 15 分钟底线防护。网络异常时保留本地缓存，下次自动合并重试。

4. **Miss_Player 偷跑行为与无意义埋点清洗**
   - 彻底移除 `FloatingButton.js` 中每次按钮渲染均上报的 `button_show` 无效事件。
   - 彻底移除 `src/index.js` 页面加载（`startScript()`）时自动预加载评论（`CommentPanel.preload()`）的偷跑逻辑，实现非激活状态零请求。

## 🧠 二、 核心经验总结 (Experiences & Learnings)

1. **Serverless / D1 写配额的极致控制模型**
   - 在 SQLite / D1 架构中，`UPSERT` 仍然算作 1 次 Write。
   - 最佳实践是将“前端频繁交互”与“后端数据库写入”**彻底解耦**：前端用高可靠的 Storage 本地持久化缓存，按固定长周期（如 1 小时）批次合并上传，后端做 JSON 增量 Merge。这能将原本每小时几十上百次的写库压缩至 **1 次/小时/用户**。

2. **数据库 JSON 字段的增量 Merge 思想**
   - 对于宽表聚合设计，`ON CONFLICT DO UPDATE SET field = excluded.field` 属于覆盖写。如果客户端前端是以 Delta（增量）发包，后端必须先 Read-Merge-Write，才能保证数据不丢失。

3. **分布式 Userscript 遥测的同源与 CORS 原则**
   - 油猴脚本运行在宿主域名上下文中，Worker 后端必须使用动态 `origin || '*'` 响应 `Access-Control-Allow-Origin`，并将自定义鉴权头（`X-MP-Token`, `X-MP-Ts`, `X-XFlow-Token`, `X-XFlow-Ts`）明确加入 `Access-Control-Allow-Headers` 白名单中。

## ⚠️ 三、 教训与避坑指南 (Pitfalls to Avoid)

### ❌ 坑点 1：切歌或视图切换时滥用 `flush()` 导致请求轰炸
- **现象**：之前在 `startSession(videoId)` 中加入 `if (currentVideoId !== videoId) this.flushSession()`，导致用户每划一个视频就发一次 POST。
- **教训**：在滑动流 UI 中，切歌属于秒级高频动作。切歌时绝不能触发网络 Flush，视频热度本身是以视频 ID 作为 key 的对象字典，天然支持在内存和 Storage 中存储多视频热度。
- **避坑法则**：**切歌只更新内存指向上，上报只走长定时器与离屏保护**。

### ❌ 坑点 2：前端预加载/初始化逻辑脱离用户意图
- **现象**：为了追求所谓的“缩短评论加载等待”，在脚本启动 `startScript()` 时无条件自动调用 `CommentPanel.preload()`。
- **教训**：用户在含有视频的网页上浏览，绝大多数情况下可能完全不需要打开播放器看评论。脚本静默预加载不仅浪费用户流量，还会引发不必要的跨域请求与垃圾遥测上报。
- **避坑法则**：**延迟按需加载 (Lazy Initialization on Demand)**。所有非核心 UI 的重型接口，必须严格限制在用户主动触发（如点击播放器、切换 Tab）后再启动。

### ❌ 坑点 3：Worker 端参数清洗正则过于苛刻破坏业务 ID
- **现象**：旧版 Worker 中的 `sanitizeStr` 采用 `replace(/[^\w\-_.]/g, '')` 且限制长度 64，导致全路径 ID `amplify_video/.../xxx.mp4` 入库时斜杠 `/` 被彻底擦除，字符串被裁切毁坏。
- **教训**：后端安全清洗不可盲目一刀切。当业务 ID 需要承载路径或特定符号时，必须在正则白名单中放行 `/` `@` `:` `=` `?` 等字符，并留足安全长度（如 256 字符）。
